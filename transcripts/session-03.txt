    ## Scope: build-order stages 1 to 3                                         
    1. **Setup:** Vite + React + TypeScript + Vitest, `.nvmrc` (Node 20), and   
  `.gitignore` (keep `BRIEF.local.md`, add `node_modules`, `dist`).             
    2. **`src/split.ts` + `src/split.test.ts`:** pure functions with no React   
  imports.                                                                      
       - Parse the total: trim, allow commas as thousands separators, reject    
  decimals, `1e5`, `12abc`, values of 0 or less, and anything over 10,000,000.  
  Each case returns the exact S-1 message.                                      
       - Validate names: trim, 1 to 30 characters, case-insensitive duplicate   
  check that includes the payer, at most 50 people. Each case returns the exact 
  S-2 message.                                                                  
       - Split: `q = Math.trunc(total / n)`, `r = total - q*n`, `friendShare =  
  r > 0 ? q + 1 : q`, payer gets `total - friendShare*(n-1)`. If the payer      
  would go below 0, return the "too small" error.                               
       - Build the message (exact S-4 text), the summary line (S-5) and the     
  `wa.me` URL.                                                                  
       - Tests: cover every S-1, S-2, S-4 and S-5 example, plus a **property    
  test** that the shares always add up exactly to the total. Use a seeded       
  random loop. Don't add fast-check without asking me.                          
    3. **Working UI for S-1 to S-8**, following `docs/ui-plan.md`:              
       - **No router.** `view: "setup" | "track"` and `sent: boolean` are       
  state, saved with the bill.                                                   
       - **Money is integers everywhere** (state and localStorage). Only a      
  valid total is saved.                                                         
       - **localStorage is a trust boundary.** Wrap every read and write in     
  try/catch, and check the shape of what you parse. Missing or damaged data     
  means an empty bill, never a crash. If storage is blocked, the app still      
  works and shows `This bill can't be saved in this browser`.                   
       - **No `alert`, `confirm` or `prompt`.** Confirmations are inline, as in 
  the plan: focus goes to Cancel, Esc cancels, and focus is restored            
  afterwards.                                                                   
       - **Accessibility:** visible labels, real `<button>`, `<input            
  type="checkbox">` and `<details>` elements, `aria-describedby` and            
  `aria-invalid` on errors, `aria-live` on the summary and copy notices, and    
  tap targets of at least 44px.                                                 
       - **Plain CSS**, following the plan's "Look" section: `system-ui` font,  
  neutral greys plus one green accent, an 8px radius, light and dark mode via   
  `prefers-color-scheme`, and a single column at most 32rem wide. Don't invent  
  any other visual style.
